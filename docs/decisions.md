# Architecture decision log

- **2026-11-02 — Private, local-first MVP:** use SQLite and exportable schema to avoid service lock-in and protect personal messages.
- **2026-11-02 — Gmail before notifications:** supported read-only API with incremental sync; notification capture remains an experimental follow-up.
- **2026-11-02 — Rules before AI:** parse standardized notification templates deterministically. Invoke the model only when useful and explicitly permitted.
- **2026-11-02 — Human approval:** no sending emails or social replies; generated CRM follow-ups are suggestions, not side effects.
- **2026-11-02 — Person-centric model (M0):** canonical chain is Person/Entity → Platform Identities → Interaction Signals → Follow-ups. Source evidence (`inbound_events`) is stored separately from inferred state; the previous event-level category/state columns are legacy, not the product model.
- **2026-11-02 — Minimal identity resolution (A1):** unresolved identities, exact email/handle matching, and manual linking only. Display names are actor candidates on signals, never identities. Suggested matches and reversible merge workflows are deferred until a real need appears.
- **2026-11-02 — Review-first follow-ups:** kind (`review|reply|waiting|follow_up`) is separate from status (`open|snoozed|done|dismissed`). A notification alone creates at most a `review` candidate.
- **2026-11-02 — Python 3.12 + Pydantic:** primary runtime is Python 3.12 (CI no longer tests 3.11); Pydantic models define the canonical domain. FastAPI arrives in A5, React/TypeScript/Vite in A5, deliberate visual design in Phase B.
- **2026-11-02 — Versioned SQLite migrations:** `PRAGMA user_version` (now v2); migrations preserve data — v1 `followups` becomes `followups_v1`, v1 cursors are copied into account-scoped `sync_state`.
- **2026-11-02 — A1 verified:** 17 tests passed, ruff clean, fixture demo idempotent on replay (3 signals + 3 review candidates, then 0 new). Committed as the M0+A1 slice.
- **2026-11-02 — A2 Gmail decisions:** macOS Keychain is the preferred OAuth token store, with a documented `0600` file fallback; Gmail source events become account-scoped via migration v3; expired `historyId` cursors get bounded recovery with explicitly recorded sync gaps (`sync_gaps`); stored excerpts capped at 200 characters by default (configurable); read-only scope only; fake transport and deterministic tests before any real account is connected.
- **2026-11-02 — A2 verified (fake transport only):** schema v3 (account-scoped events rebuilt with data + FK integrity preserved), Gmail connector (initial/incremental, pagination, add/delete with signal withdrawal, duplicate replay, transactional cursor, 404 bounded recovery + recorded gap, 429 retry, 401 explicit failure, crash-commits-nothing), Keychain/0600 token stores, CLI `auth`/`sync`/`status`. 37 tests passed, ruff clean. No real Gmail account connected; live OAuth is a separate approved step.
- **2026-11-02 — A2 live acceptance passed (test mailbox only):** after a post-A2 audit hardened real-path defects (message-deleted-404 skip, quota-403 retry, refresh-error mapping, SENT/DRAFT exclusion, corrupt-token and Keychain failure handling; 45 tests, ruff clean), the controlled procedure against the dedicated test mailbox passed end to end: OAuth read-only via Keychain, bounded 30-day initial sync (7 new), duplicate-free incremental re-sync, new-message ingestion (cursor 2281 → 2464), Trash as label change (no withdrawal), permanent deletion as signal withdrawal with evidence preserved. No polling, no primary account, no external inference. 404 expired-cursor recovery remains covered by fake-transport tests only, not yet exercised live.
- **2026-11-02 — A3 verified-origin parsers:** a signal's `platform` now means *verified origin* — asserted only when the sender address is on a trusted platform domain; wording mentioning a platform is never proof of origin. Actor/handle extraction happens only under verification with conservative patterns; senders claiming a platform without a verified domain, automated senders, and unrecognized mail degrade to `platform="unknown"` (`unclassified_email` / `automated_notification`) and create no review follow-ups. Parser registry is versioned per platform (`<platform>-notifications` v1, `generic-email` v1) and stamped on each signal. Signal dedupe keys are now event-scoped (not parser-scoped), so parser upgrades cannot duplicate historical signals or follow-ups. Quality is measured on a synthetic corpus (`fixtures/parser-corpus.json`) with per-platform precision/recall and a zero-fabricated-identity invariant. Verified: 78 tests passed (33 parser-corpus), Ruff clean; one pre-existing environment-dependent A2 CLI test (assumed the `[gmail]` extra absent, which the live acceptance installed) was made deterministic in the same pass.
- **2026-11-02 — A5 ordering and API shape:** A5 (web app) proceeds before A4 (LLM enrichment). The FastAPI layer is thin over the existing storage repositories and Pydantic models — no ORM, no new tables, versioned `/api/v1` contracts kept separate from frontend presentation. A5a (read-only endpoints) verified: 86 tests passed, Ruff clean, all against isolated synthetic databases. Note the A3 parser matches sender domains only; it does not evaluate SPF/DKIM/DMARC, and product copy must not claim authenticated origin.
- **2026-11-02 — A5b follow-up transitions and local mutation guard:** follow-up state changes are a storage-level state machine (open ⇄ snoozed with required `snoozed_until`, resolve stamps `resolved_at`, reopen clears it, resolved items must reopen before snoozing); mutation endpoints additionally require a localhost Host and, when present, a localhost Origin, because CORS alone is not a security boundary. Verified: 94 tests passed, Ruff clean.
- **2026-11-02 — A5 complete:** the local web app ships as five small slices (read API, mutation API, shell + Today/People, Person Detail/Follow-ups/Sources with notes editing, production build served by FastAPI + Playwright golden path). Final evidence: 99 backend tests passed, Ruff clean, 5 frontend component tests passed, typecheck clean, production build succeeds, and the Playwright golden path passes against an isolated synthetic database. No Gmail, polling, or external inference was used. Identity unlinking stays deferred (identity-derived vs manually assigned person attribution is not yet distinguishable), and Authentication-Results capture stays a future ingestion hardening item.
- **2026-11-02 — A6-1 attribution precedence:** explicit user decisions outrank exact identity matches, which outrank parser inference. Two defects were found by regression tests and fixed: attaching an already-observed unresolved identity via `add_identity` silently returned it unlinked (it now performs the manual link with backfill), and `link_identity` backfill overwrote signals a user had manually assigned to someone else (it now backfills only unassigned signals/follow-ups and rejects identities owned by another person with an error the API maps to 409). No schema change was needed because manual assignments and links share the same confirmed-state columns.
- **2026-11-02 — A6-2 deletion consistency:** permanent source deletion preserves evidence and withdrawn signals while auto-dismissing only open rule-created review candidates on newly withdrawn signals. Confirmed obligations, user-created and snoozed reviews, resolved follow-ups, and deliberate reopenings remain untouched. Gmail event inserts, withdrawals, dismissals, and cursor advancement share one SQLite transaction through `commit_sync_batch`, while the standalone withdrawal path remains idempotent. No schema change was needed because follow-up kind, status, and `created_by` already encode the policy distinction. Verification supplied for this slice reports 9 new deletion tests and 112 full-suite tests passing, with the single Ruff unused-variable finding corrected. The remaining Starlette and httpx deprecation warning is dependency maintenance outside this slice.
- **2026-11-03 — A6-3 activity noise gate:** routine `platform_activity` remains interaction evidence but no longer creates review candidates. Only `direct_message_notification` and `direct_email` create candidates, because only those kinds reasonably indicate direct interpersonal outreach from a notification alone. The insertion-time gate never deletes existing follow-ups, so user-created and user-confirmed obligations survive tightening and replay. Generic promotion and marketing senders are now automated evidence under `generic-email` parser version 2, and the synthetic corpus covers verified LinkedIn promotion plus generic promotion cases. Red evidence was 5 failed and 1 passed against the prior gate; green evidence is 57 focused tests, 120 full-suite tests, Ruff clean, and 1 Playwright golden-path test passing. The known Starlette and httpx deprecation warning remains separate dependency maintenance.
- **2026-11-03 — A6-4 crash consistency:** the Gmail batch commit remains the strong atomic unit for event inserts, withdrawals of previously derived signals, candidate dismissals, and cursor advancement. Signal derivation remains a separate self-healing step, so a crash after the batch commit is eventually consistent rather than immediately complete until the next successful sync. Incremental sync now repairs underived signals before applying deletions, closing the case where a message deleted while underived was recreated as active. Manual assignments, confirmed obligations, withdrawn signals, and dismissed candidates survive repair, replay, and database reconnection. Two narrow windows are documented without overstating atomicity: a message first added and deleted in the same unseen history batch can still derive after withdrawal, and expired-cursor gap recording remains a separate write after recovered batch commit. Red evidence was 2 failed and 4 passed against the prior connector; green evidence is 15 focused recovery and deletion tests, 126 full-suite tests, Ruff clean, and 1 Playwright golden-path test passing. The known Starlette and httpx deprecation warning remains separate dependency maintenance.
- **2026-11-03 — A6-5 recovery-gap atomicity:** expired-cursor recovery now commits recovered events, cursor advancement, the `sync_gaps` row, and `last_recovery_at` in one SQLite transaction through `commit_sync_batch`. A failure while recording the gap rolls back the recovered batch and cursor, while signal derivation remains a separate self-healing step rather than part of that transaction. Repeated recovery replays events without duplicating signals or follow-ups, and each distinct later expiration records its own gap. The remaining documented limitation is unchanged: a message first added and permanently deleted inside the same previously unseen history batch can still derive after the batch withdrawal because no stored signal existed when withdrawal ran. Red evidence was 1 failed and 1 passed against the prior two-transaction recovery; green evidence is 22 focused tests, 128 full-suite tests, Ruff clean, and 1 Playwright golden-path test passing. The known Starlette and httpx deprecation warning remains separate dependency maintenance.
- **2026-11-03 — Deferred Gmail same-batch add/delete tombstone:** the same-batch limitation above remains open engineering work, not a resolved A6 guarantee. Closing it would require recording deletion tombstones for previously unseen events or otherwise suppressing later derivation for events deleted in that batch, with dedicated fake-transport crash and replay tests. It is deferred beyond A6 and is not addressed by Phase B UI work.
